0. АВТОРИЗАЦИЯ В АДМИН ПАНЕЛИ
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/admin/login
Auth:   Bearer <user_jwt_token>   ← ОБЯЗАТЕЛЬНО, токен текущего пользователя

Тело (plain JSON, не зашифровано):
{
  "password": "<sha256(admin_password)>"
}
Примечание: пароль хешируется SHA-256 от введённой строки (без email-соли).

Ответ:
{
  "success": true,
  "token":   "<admin_session_token>"   // опционально, если сервер выдаёт отдельный токен
}
или
{
  "success": false,
  "error":   "Invalid password"
}

Логика на сервере:
  1. Проверить Authorization header — убедиться что пользователь авторизован
  2. Проверить что пользователь имеет флаг is_admin = true
  3. Проверить admin password hash
  4. Вернуть success

Auth:   Bearer <jwt>

Тело (зашифрованный JSON):

  "action": "pause"    // pause | resume | cancel
}

Действия:
  pause  → установить is_active = false (приостановить)
  resume → установить is_active = true  (возобновить)
  cancel → установить tariff = "Trial", сбросить subscription_expiry

  При активации Hour сервер должен установить:
    subsEndDate = now + 3600  (Unix timestamp, +1 час)
    used_traffic = 0
  Тариф считается активным пока: subsEndDate > now И used_traffic < 1 073 741 824

Ответ:
{
  "success": true
}

URL:    /api/admin/users
Auth:   Bearer <jwt>

Ответ:
{
  "success": true,
  "data": [
    {
      "id":                  123,
      "email":               "user@example.com",
      "tariff":              "Advanced",
      "is_new":              false,
      "email_confirmed":     true,
      "create_date":         "2026-01-01",
      "subscription_expiry": "2026-06-01",
      "is_active":           true,
      "used_traffic":        2147483648,    // НОВОЕ: байты использованного трафика
      "traffic_limit":       10737418240    // НОВОЕ: байты лимита тарифа (0 = безлимит)
    }
  ]
}

================================================================================
  ТАРИФЫ (справочник)
================================================================================
  Trial    — 7 дней, безлимитный трафик
  Unlimited — бессрочно, безлимитный трафик
  Basic    — 30 дней, лимит 3 ГБ  (3 221 225 472 байт)
  Advanced — 30 дней, лимит 10 ГБ (10 737 418 240 байт)
  Premium  — 365 дней, безлимитный трафик
  Hour     — 1 час, лимит 1 ГБ (1 073 741 824 байт), выдаётся за рекламу
             subsEndDate = now + 3600 секунд, активен пока не истёк час И не исчерпан трафик

================================================================================
  ШИФРОВАНИЕ — алгоритм (Python сторона)
================================================================================
  import base64, os
  from Crypto.Cipher import AES
  from Crypto.Util.Padding import pad, unpad
  import hashlib

  def get_key(token: str) -> bytes:
      return hashlib.sha256(token.encode('utf-8')).digest()[:16]

  def encrypt(plaintext: str, token: str) -> str:
      key = get_key(token)
      iv = os.urandom(16)
      cipher = AES.new(key, AES.MODE_CBC, iv)
      ct = cipher.encrypt(pad(plaintext.encode('utf-8'), AES.block_size))
      return base64.b64encode(iv + ct).decode('utf-8')

  def decrypt(b64data: str, token: str) -> str:
      key = get_key(token)
      raw = base64.b64decode(b64data)
      iv, ct = raw[:16], raw[16:]
      cipher = AES.new(key, AES.MODE_CBC, iv)
      return unpad(cipher.decrypt(ct), AES.block_size).decode('utf-8')

10. СИНХРОНИЗАЦИЯ ТРАФИКА ПОЛЬЗОВАТЕЛЯ
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/v1/user/sync-traffic
Auth:   Bearer <user_jwt_token>

Назначение:
  Клиент отправляет текущее суммарное потребление трафика за период тарифа.
  Вызывается в двух случаях:
    1. При каждом нажатии кнопки "Авто" — перед запуском авто-режима
    2. Если локальная БД показывает превышение лимита — немедленная отправка
       с последующей блокировкой кнопки Авто

Тело (зашифрованный JSON):
{
  "used_traffic": 2147483648   // байты, суммарный трафик за период тарифа
}

Ответ (успех, с обновлёнными данными пользователя):
{
  "success": true,
  "enc":     true,
  "data":    "<encrypted>"
}

Расшифрованный data (опционально, если сервер возвращает обновлённые данные):
{
  "tariff":        "Advanced",
  "subsEndDate":   "2026-06-30",
  "used_traffic":  2147483648,
  "traffic_limit": 10737418240,
  "isActive":      true
}

Ответ (ошибка):
{
  "success": false,
  "error":   "описание ошибки"
}

Логика на сервере:
  1. Получить user_id из JWT токена
  2. Расшифровать тело запроса
  3. Обновить поле used_traffic в БД для данного пользователя
  4. Проверить: used_traffic >= traffic_limit?
       - Если да → установить флаг "трафик исчерпан", при необходимости
         деактивировать тариф (для Hour — сбросить subsEndDate)
  5. Вернуть актуальные данные пользователя (тариф, лимит, остаток)

Примечание:
  Клиент НЕ доверяет только локальным данным — перед каждым запуском
  авто-режима он синхронизирует трафик с сервером и получает актуальный
  лимит. Если сервер подтверждает превышение — авто-режим блокируется
  даже если локальная БД показывала допустимое значение.

11. ПОЛЕ group В КОНФИГАХ (расширение существующих эндпоинтов)
────────────────────────────────────────────────────────────────────────────────
Затрагивает эндпоинты:
  GET /api/v1/users/configs       (AuthApiService.getClientFilesList)
  GET /api/admin/users/<id>/configs (AdminApiService.getClientFilesList)

Каждый объект в массиве files теперь должен содержать поле "group":

{
  "name":     "antizapret.ovpn",
  "type":     "openvpn",
  "category": "antizapret",
  "protocol": "udp",
  "content":  "<содержимое конфига>",
  "group":    "auto1"    ← НОВОЕ поле
}

Значения поля group:
  "auto1" — основной авто-режим (кнопка "Авто")
  "auto2" — резервный авто-режим (кнопка "Авто 2", будет добавлена позже)
  null    — не указано, клиент считает "auto1"

Логика на клиенте:
  - При загрузке конфигов поле group сохраняется в колонку autoGroup таблицы
    vpn_server_configs (миграция БД 7→8)
  - Кнопка "Авто" запускает startAutoMode(group = "auto1")
  - Если в группе "auto1" нет конфигов — используются все конфиги (fallback)
  - Кнопка "Авто 2" запустит startAutoMode(group = "auto2") — пока не добавлена

Логика на сервере:
  - Сервер сам решает какие конфиги в какую группу попадают
  - Рекомендация: auto1 = antizapret/обход блокировок, auto2 = прямой VPN
  - Если поле group не нужно — просто не возвращать его (клиент использует auto1)

11. СПИСОК КОНФИГУРАЦИЙ ПОЛЬЗОВАТЕЛЯ — поле "group" для авто-режимов
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/v1/users/configs
Auth:   Bearer <user_jwt_token>

Тело (зашифрованный JSON):
{
  "email": "user@example.com"
}

Ответ (зашифрованный, enc=true). Расшифрованный data:
{
  "files": [
    {
      "name":     "Server-NL-1",
      "path":     "...",
      "size":     1234,
      "modified": 1717000000.0,
      "type":     "openvpn",        // openvpn | wireguard | amneziawg
      "category": "antizapret",     // antizapret | antizapret-tcp | vpn | vpn-tcp | ...
      "protocol": "udp",
      "config":   "...",
      "content":  "<полный текст конфига>",
      "group":    "auto1"           // НОВОЕ ПОЛЕ: "auto1" | "auto2" | null
    }
  ]
}

Поле "group":
  - Определяет к какому авто-режиму относится конфиг.
  - "auto1" (или null/отсутствует) — основной авто-режим (кнопка "Авто").
  - "auto2" — резервный авто-режим (вторая кнопка, если включена).
  - Клиент при логине сохраняет все конфиги в локальную БД с этим полем.
  - Авто-режим перебирает конфиги только своей группы в порядке:
      type:     openvpn → wireguard → amneziawg
      category: antizapret → antizapret-tcp → antizapret-udp → vpn → vpn-tcp → vpn-udp

ВАЖНО (оптимизация загрузки конфигов):
  - Конфиги запрашиваются ОДИН раз при логине и кешируются в локальной БД клиента.
  - При onResume / повторных запусках клиент НЕ обращается к серверу за конфигами,
    а читает их из локальной БД.
  - Принудительная перезагрузка происходит только при новом логине.
  - Рекомендуется: сервер может вернуть поле "configs_version" или "configs_hash"
    в ответе /api/v1/login/update, чтобы клиент понимал когда нужно перезагрузить
    конфиги (если на сервере они изменились). Это опционально, но ускорит работу.

12. СИНХРОНИЗАЦИЯ ТРАФИКА — обязательна для лимитных тарифов
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/v1/user/sync-traffic   (см. также раздел 10)
Auth:   Bearer <user_jwt_token>

Клиент отправляет used_traffic в следующих случаях:
  1. При отключении VPN-сессии (сохранение израсходованного трафика).
  2. Перед запуском авто-режима (проверка остатка лимита).
  3. Периодически при активном подключении на лимитном тарифе.

Тело (зашифрованный JSON):
{
  "used_traffic": 2147483648   // суммарно израсходовано за период тарифа, байты
}

Ответ (зашифрованный, enc=true). Расшифрованный data:
{
  "tariff":        "Advanced",
  "subsEndDate":   "2026-06-30",
  "used_traffic":  2147483648,   // сервер может скорректировать (источник правды)
  "traffic_limit": 10737418240,
  "isActive":      true
}

Логика на сервере:
  1. Обновить used_traffic пользователя (взять max(локальное, серверное) или серверную логику).
  2. Если used_traffic >= traffic_limit → пометить тариф исчерпанным.
  3. Вернуть актуальные значения — клиент применит их и заблокирует кнопку "Авто"
     при исчерпании трафика или истечении срока.

11. ОБНОВЛЕНИЕ JWT ТОКЕНА (фоновый рефреш без переавторизации)
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/v1/token/refresh
Auth:   Bearer <текущий_jwt_token>

Назначение:
  Вызывается при onResume главного экрана и экрана Аккаунт, если срок
  действия токена подходит к концу. Позволяет обновить токен в фоне,
  чтобы пользователю не пришлось заново авторизоваться в приложении.
  При ошибке клиент продолжает работать со старым токеном (некритично),
  переавторизация НЕ происходит.

Тело (plain JSON):
{}

Ответ (успех):
{
  "success":     true,
  "token":       "<новый_jwt_token>",
  "tokenExpiry": "2026-07-30"           // опционально, формат yyyy-MM-dd
}

Ответ (ошибка):
{
  "success": false,
  "error":   "Token expired" | "Invalid token"
}

Логика на сервере:
  1. Проверить текущий токен из заголовка Authorization
  2. Если токен ещё валиден (даже близок к истечению) — выдать новый
  3. Если токен полностью истёк/невалиден — вернуть success=false
     (клиент покажет экран логина только при явной 401 на других запросах)

13. ОБНОВЛЕНИЕ ДАННЫХ ПОЛЬЗОВАТЕЛЯ (обновлённый формат ответа)
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/v1/login/update
Auth:   Bearer <user_jwt_token>

Назначение:
  Получение актуальных данных пользователя при onResume и периодически.
  Возвращает ВСЕ данные пользователя и тарифа, включая актуальный
  объём трафика (используемый и максимальный). Клиент полностью
  доверяет этим значениям и перезаписывает локальную БД.

Тело (зашифрованный JSON):
{
  "email": "user@example.com"
}

Ответ:
{
  "success": true,
  "enc":     true,
  "data":    "<encrypted>"
}

Расшифрованный data (ОБНОВЛЁННЫЙ — добавлены поля трафика):
{
  "user_id":       123,
  "email":         "user@example.com",
  "tariff":        "Advanced",
  "isConfirmed":   true,
  "isNew":         false,
  "isActive":      true,
  "isAdmin":       false,
  "subsEndDate":   "2026-06-30",        // формат yyyy-MM-dd
  "tokenExpiry":   "2026-07-30",        // формат yyyy-MM-dd
  "createdAt":     "2026-01-01",        // формат yyyy-MM-dd
  "used_traffic":  2147483648,          // НОВОЕ: байты использованного трафика
  "traffic_limit": 10737418240          // НОВОЕ: байты лимита (0 = дефолт тарифа, -1 = безлимит)
}

ВАЖНО про traffic_limit:
  Это поле может МЕНЯТЬСЯ (администратор может увеличить/уменьшить лимит).
  Клиент НЕ использует статичный лимит из тарифа, а берёт значение сервера:
    traffic_limit = 0   → использовать дефолтный лимит тарифа (3/10 ГБ и т.д.)
    traffic_limit > 0   → явный лимит от сервера (переопределяет тариф)
    traffic_limit = -1  → безлимит (переопределён администратором)

14. СПИСОК КОНФИГОВ ПОЛЬЗОВАТЕЛЯ (обновлённый — добавлено поле group)
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/v1/users/configs
Auth:   Bearer <user_jwt_token>

Тело (зашифрованный JSON):
{
  "email": "user@example.com"
}

Ответ:
{
  "success": true,
  "enc":     true,
  "data":    "<encrypted>"
}

Расшифрованный data:
{
  "files": [
    {
      "name":     "antizapret-russia",
      "path":     "/configs/...",
      "size":     2048,
      "modified": 1717000000.0,
      "type":     "openvpn",            // openvpn | wireguard | amneziawg
      "category": "antizapret",         // antizapret | vpn | ...
      "protocol": "udp",
      "config":   "...",
      "content":  "<содержимое конфига>",
      "group":    "auto1"               // НОВОЕ: auto1 | auto2 — группа авто-режима
    }
  ]
}

Назначение поля group:
  Определяет к какой кнопке "Авто" относится конфиг.
  Позволяет поддержать второй авто-режим (например auto1 = antizapret,
  auto2 = прямой VPN). Если поле отсутствует — конфиг попадает в "auto1".
  Клиент сохраняет это в поле autoGroup таблицы vpn_server_configs.

15. СИНХРОНИЗАЦИЯ ТРАФИКА (уточнение — вызывается чаще)
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/v1/user/sync-traffic
Auth:   Bearer <user_jwt_token>

(Формат запроса/ответа — см. раздел 10 выше)

Уточнение по моментам вызова:
  Клиент отправляет used_traffic на сервер в следующих случаях:
    1. Перед каждым запуском авто-режима (проверка лимита)
    2. После каждой VPN-сессии (при отключении), только для лимитных тарифов
    3. Периодически во время активного соединения (мониторинг каждые 5 сек,
       отправка при изменении)
  Сервер в ответе возвращает актуальные tariff/subsEndDate/used_traffic/
  traffic_limit/isActive — клиент применяет их и при превышении лимита
  блокирует подключение и кнопку Авто, сбрасывает активную конфигурацию.

11. ОБНОВЛЕНИЕ ТОКЕНА (фоновый рефреш)
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/v1/token/refresh
Auth:   Bearer <текущий_jwt_token>

Тело: {} (пустой JSON)

Ответ:
{
  "success": true,
  "token": "<новый_jwt_token>",
  "tokenExpiry": "2026-12-31"   // дата истечения нового токена (yyyy-MM-dd)
}

Логика на сервере:
  1. Проверить текущий токен из заголовка Authorization
  2. Если валиден (или истёк недавно, в пределах grace-периода) — выдать новый
  3. Вернуть новый токен + дату истечения
  Цель: пользователь не должен переавторизовываться вручную при истечении токена.

12. ЗАГРУЗКА ПОЛЬЗОВАТЕЛЬСКОГО КОНФИГА НА СЕРВЕР (синхронизация)
────────────────────────────────────────────────────────────────────────────────
Метод:  POST
URL:    /api/v1/user/configs/upload
Auth:   Bearer <jwt_token>

Тело (зашифрованный JSON):
{
  "name":        "Мой конфиг",
  "type":        "OpenVPN",          // OpenVPN | WireGuard
  "server_host": "vpn.example.com",
  "content":     "<полное содержимое конфига>"
}

Ответ:
{
  "success": true
}

Логика на сервере:
  1. Получить user_id из JWT
  2. Расшифровать тело
  3. Проверить нет ли уже такого конфига (по name+content или хешу content)
  4. Если нет — сохранить как пользовательский конфиг
  Примечание: клиент отправляет конфиги при добавлении и при свайпе-синхронизации
  на странице конфигов. Дубликаты сервер должен игнорировать.
